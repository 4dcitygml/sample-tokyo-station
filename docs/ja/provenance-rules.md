# 出典・根拠の記録ルール（provenance）

属性値・幾何・テクスチャの「出典・根拠」をどこに・どの粒度で記録するかの規約。

English (canonical): [docs/provenance-rules.md](../provenance-rules.md)

> **適用範囲の注記**: 本規約は i-UR ADE（`uro:` — PLATEAU が採用する拡張）を使う
> CityGML データセット向けに設計されています（層1の機構は i-UR 由来）。他のデータセットに
> 基づく都市リポジトリ（`4dcitygml.json` の `building_id` 参照）は、層1をそのデータセットの
> 品質メタデータ機構に読み替えたうえで、同じ三層原則を適用します。

## 位置づけ — i-UR（urban ADE）＋α の運用

本規約は**新しいスキーマを一切足さず**、既存の標準機構だけで「項目単位の出典」を成立させる
運用（規約＋ツール）である。土台は2つの標準:

- **i-UR（uro＝Urban Object ADE）** — PLATEAU が採用する CityGML の拡張。
  `uro:DataQualityAttribute`（取得方法・精度・仮/確定）と `uro:thematicSrcDesc`
  （主題属性の出典コード表）を**建物単位**で提供する。これが層1。
- **CityGML 本体の generics**（`gen:genericAttributeSet`） — 「標準属性が無い場合」に使う
  汎用機構。i-UR の建物単位より**細かい項目単位**の出典を、規格適合のまま持たせる受け皿。
  これが層2の「＋α」。

つまり「**ADE の品質属性（建物単位）を主軸に、generics で項目単位の特記を足す（＋α）**」
という二段構えであり、独自 ADE やスキーマ拡張は行わない（相互運用性を壊さない＝「巨人の
肩の上」）。層1と層2が**同一コード表**を共有することで、両者は「建物既定＋その例外」という
一貫した意味体系になる（→ 下記「解決規則」）。運用は属性エディタで実装済み（→ §5）。

## 0. 原則 — 三層で記録する

| 層 | 記録するもの | 場所 | 粒度 | 位置づけ |
|---|---|---|---|---|
| **1. 公式品質属性** | 取得方法・精度・仮/確定の区分 | `uro:DataQualityAttribute` | 建物 ×（軸 × LOD） | **主**・規格標準を最優先 |
| **2. gen「出典」セット** | 属性↔出典の**個別対応**・根拠資料リンク | `gen:genericAttributeSet name="出典"` | **項目（属性）単位** | **例外**・必要な場合のみ |
| **3. git 履歴** | 誰が・いつ・なぜ（経緯の全体） | commit / PR / `Building:` trailer | 葉値単位（最小差分パイプラインが保証） | **常時・自動** |

役割分担: データが単体で流通しても残るのは層1・2。リポジトリ文脈での完全な経緯
（blame・PR 議論・再現手順）は層3。

## 1. 層1 — 公式品質属性（主・原則こちらを使う）

公式で書ける粒度の上限（i-UR 3.1 / 3.2 共通）:

| 軸 | 要素 | 粒度 |
|---|---|---|
| 幾何の出典 | `geometrySrcDescLod0`〜`Lod4` | 建物 × LOD別 |
| 外観の出典 | `appearanceSrcDescLod0`〜`Lod4` | 建物 × LOD別 |
| 高さの取得方法 | `lod1HeightType` | 建物ごと（実測系 1-8,10 / 仮系 0,9） |
| 精度 | `srcScaleLod*` | 建物 × LOD別 |
| **属性（主題）の出典** | `thematicSrcDesc` | **建物ごとに一括列挙**（属性名との対応は書けない） |

ルール:

- **R1-1（同時更新）**: 値を変える PR では、対応する品質コードを**同一 PR で同時更新**する。
  例: measuredHeight を実測値に置き換えたら、`lod1HeightType` を仮系（0/9）→実測系へ更新する。
- **R1-2（由来コードの追記）**: 新しい出典から属性を追加・更新した建物では、
  `thematicSrcDesc` に由来コードを追記する（建物単位。コードは同梱 codelist から）。
- **R1-3（値エンコード禁止）**: 出典・精度の情報を値に埋め込まない（`10000100m` のような
  独自エンコードは不可。-9999 センチネルの教訓）。

## 2. 層2 — gen「出典」セット（例外・項目単位）

### 使う条件（いずれかに該当する場合のみ）

- 複数出典が混在し、建物単位の列挙では「どの属性がどの出典か」が読めない
- 市民・現地からの個別の実測・資料提供など、**由来の明示自体に価値がある**値
- 導出属性で、属性↔導出元の対応を残す必要がある

### 使わない条件

- 層1（標準の受け皿）で足りる場合。generics の XSD 注記どおり「標準属性が無い場合に限る」。
  全属性への機械的な併記はしない。

### フォーマット（規約）

```xml
<gen:genericAttributeSet name="出典">
    <gen:stringAttribute name="bldg:measuredHeight">
        <gen:value>801</gen:value>
    </gen:stringAttribute>
    <gen:stringAttribute name="bldg:storeysAboveGround">
        <gen:value>802</gen:value>
    </gen:stringAttribute>
    <gen:uriAttribute name="根拠資料:bldg:measuredHeight">
        <gen:value>https://github.com/4dcitygml/sample-tokyo-station/pull/2</gen:value>
    </gen:uriAttribute>
</gen:genericAttributeSet>
```

この例の意味: measuredHeight は `801`（現地調査）由来・storeysAboveGround は
`802`（写真判読）由来。

- **R2-1（セット名）**: セットは `name="出典"` 固定・**1建物に1つまで**。
- **R2-2（キー）**: 子要素の `@name` は**対象属性の QName**（例 `bldg:measuredHeight`、
  `uro:buildingStructureType`）。同名要素が複数箇所にありうる場合は diff パイプラインの
  葉パス表記を使う。
  - QName が一意かは**建物単位で機械的に判定**する: CityGML 本体属性は XSD で
    `maxOccurs=1` ＝規格保証で常に一意。ADE 属性は構造的に繰り返し可能なものがある
    （KV 対・災害リスクの繰り返し等）。属性エディタはこの動的判定を実装しており、
    一意な属性のみ QName 特記を許可する。
- **R2-3（値はコード表から選択）**: 値は**対象データセットの
  `codelists/…thematicSrcDesc….xml` のコード値のみ**（自由記述は不可）。層1の
  `thematicSrcDesc` と**同じ語彙**を項目単位に適用する（例: `801`=現地調査・
  `802`=写真判読・`803`=GISデータ演算）。機械検証（コード表との突き合わせ lint）と
  和名解決にそのまま乗せるための規約。
  - 手段・日付などの詳細は値に書かない → 根拠資料リンク（R2-4）と PR 本文（層3）へ。
    仮/確定の区分は層1の品質コードへ（矛盾させない）。
  - コード表に無い出典 → `700`（その他の資料）等の受け皿コード＋**根拠資料リンク必須**。
    恒常的に必要な出典が現れたら、**コード表自体の拡張を PR で提案**する
    （コード表も git 管理下＝レビュー対象）。
- **R2-4（根拠資料リンク）**: `gen:uriAttribute` の `@name` は `根拠資料`（建物全体）
  または `根拠資料:<QName>`（項目対応）。PR・写真・台帳等への URL。
- **R2-5（配置）**: 実データの generics 配置に合わせ **`core:creationDate` 直後**に置く。
- **R2-6（値は書かない）**: セットに書くのは出典情報のみ。値そのものは標準属性側に置く
  （重複させない）。
- **R2-7（同時更新）**: 対象属性の値を直したら、対応する出典コードも**同一 PR で更新**する。

### 出典の解決規則（特記 ＞ 上位）

層1と層2が**同一コード表**であることにより、任意の属性の出典は次の規則で一意に解決できる:

1. **特記あり** — 「出典」セットに当該属性（QName）の特記があれば、そのコードが出典（一意）。
2. **特記なし** — 建物の `thematicSrcDesc`（上位）を参照する。
   - 上位が**1コード**なら出典は一意。
   - 上位が**複数コード**なら出典は「そのいずれか」（候補集合）。対応を確定させたい属性に
     だけ特記を追加すれば、**建物全体を書き換えずに漸進的に一意化**できる。
3. どちらにも無ければ `898`（不明）相当として扱う。

- **R2-8（特記⊆上位の不変条件）**: 特記に使う出典コードは、**上位 `thematicSrcDesc` にも
  含まれていなければならない**。新しい出典を特記で導入する場合は、上位への同コード追記
  （R1-2）を同一 PR で行う。これにより上位は常に「この建物の属性出典の完全な集合」、
  特記は「その中の対応付け」となり、両者が矛盾しない。この包含関係は機械検証できる。

### 検証・パイプラインとの関係（実証済み）

- 上記フォーマットは **CityGML 2.0 ＋ i-UR 3.2 の XSD で valid**（オフライン validate で
  確認済み）。
- diff パイプラインは特記を
  `/genericAttributeSet[@name=出典]/stringAttribute[@name=…]/value` の**葉単位パス**として
  検出する。＝出典の追記・更新は既存のレビューパイプライン（建物単位 PR・最小差分）に
  **追加実装なしで乗る**。
- 前例: PLATEAU 公式配布自体が自治体独自属性を `gen:stringAttribute` で大量収録しており、
  generics の利用は公式運用の延長線にある。

## 3. 層3 — git 履歴（常時・自動）

- コミットに `Building: <uro:buildingID>` trailer（`scripts/suggest_commit.py`）。
  最小差分ゲートが葉値単位 diff を保証するため、**`git blame` が属性粒度で効く**。
- 導出・変換で属性を作った場合は、**導出方法・パラメータ・再現手順を PR 本文**に記録する
  （第三者が同一結果を得られること）。
- 経緯の説明（なぜこの値にしたか）は PR の説明・レビュー議論に残す。データ内には書かない。

## 4. 横断的な属性追加 PR のルール

新属性を一括追加する PR では:

1. 標準の受け皿がある属性 → **標準属性**として追加し、`thematicSrcDesc` に由来コードを
   追記（R1-2）
2. 属性↔出典の対応が重要（複数由来の混在・導出属性） → 「出典」セットを併記（層2）
3. 導出方法・パラメータ → PR 本文に記録（層3）

## 5. 属性エディタでの運用（実装済み）

属性エディタは本規約を UI として実装している。提出者は規約の条文を読まずに、画面操作だけで
規約準拠の出典を記録できる。

- **建物既定を1回だけ表示**: 建物 ID の直下に「出典（この建物の既定）」＝上位
  `thematicSrcDesc`（コード＋和名）を1回表示する。建物単位で共通の出典を全属性行に
  繰り返さない（解決規則の「特記なし＝上位参照」を UI 化）。
- **値変更後の次操作を出典選択に固定**: 属性値を確定すると同じ行に出典の必須選択欄を展開し、
  そこへフォーカスする。変更した全属性の出典が揃うまで「変更内容を送る」は無効とし、
  送信 API でも同じ条件を再検証する。`898 不明`・`999 未作成` は新しい変更の根拠として
  選べない。
- **特記は該当属性の行だけ**: 未変更の属性は、出典が既定と異なる行だけ表示する。
- **プルダウンはコード＋和名**: 値は自由記述させずコード選択に限定する（R2-3 の同一コード表）。
- **R2-8 を自動化**: 特記に選んだコードが上位 `thematicSrcDesc` に無ければ、保存時に上位へ
  自動追記し（同一 PR 内）、既定バーに予告表示する。特記⊆上位の不変条件が UI で保たれる。
- **曖昧な属性も選択必須**: 同一建物内で QName が重複する属性は gen の項目特記を作れないため、
  選択コードを建物既定へ同期し、属性との対応を自動生成する PR 本文（git 履歴）へ残す。
- **PR 説明を自動生成**: 選択した出典と変更前後から概要と確認表を生成する。利用者が入力する
  のは任意の補足・根拠資料 URL だけとし、非技術者向けの主文には XML タグ名を出さない。
- **バイト保持・パイプライン整合**: 特記の挿入は `core:creationDate` 直後（R2-5）に、原文の
  字下げ・改行・BOM を保ったまま追記する。変更は建物単位 PR のパイプラインにそのまま乗る。
